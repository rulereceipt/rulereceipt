What the false-accusation number means

There are two measurements, and they answer different questions.

The frozen public corpus. fa-corpus v1–v4 is a committed, synthetic, redacted set of 170 checks — near-misses a careful checker must stay quiet on, each paired with a real violation it must catch. Run every rules file against every session and count any FAIL: 0 of 170. Anyone can reproduce it from the repo alone with npx tsx scripts/false-accusation-rate.ts --frozen (and --v2, --v3, --v4); it only moves when the checkers change. A fifth set (v5) locks 14 plain-prose branch-rule near-misses in the test suite, for 0 of 184 in all.

Real third-party rules files against real sessions. We ran 559 real rules files (other people's projects) against 5 of the maintainer's own sessions — 2,795 reports — and hand-checked every FAIL. On 0.1.112 (measured 2026-10-18), 0.4% carried a FAIL (12 reports), down from 2.9% in September 2026. Every one was a real action — a real push to main, a new Date() actually written to a file — matched against a rule from a different project; that is the measured ceiling, not a misread. (Before 0.1.106, 5 of 26 “broken” verdicts on the maintainer's sessions were wrong, all from one cause — a rule word matching unrelated code — fixed in 0.1.106.) The sessions are private; the corpus list is committed, so the method is rerunnable.

What the detection number means

Precision alone can be gamed by never accusing anything. So there is a second set: hand-labelled sessions that genuinely break a rule (a push to main, an edit to .env, a console.log written into a file, a "tests pass" claim contradicted by a failing run, a forbidden import) — alongside near-misses that must not fire (a push to a feature branch, editing .env.example, a command that only mentions git push). It is a sanity check across the checkers, not a real-world detection rate. Every violation is caught; every near-miss stays quiet.

Run it yourself

The strongest version of this claim is the one you check. The self-test ships in the CLI and makes zero network calls — watch it with lsof or Little Snitch:

npx rulereceipt@latest selftest

The full precision and detection measurements are ordinary scripts in the open repository — clone it and run them against your own corpus and sessions.

A "FAIL" comes only from hard evidence — a forbidden action that actually happened, or the agent's own claim contradicted by the session's own logs. That's a build-enforced invariant, not a convention (a build test fails if a FAIL is created any other way). An AI opinion (with --llm) is labelled as an opinion and never counted as a verdict. When the evidence doesn't settle a rule, the answer is "couldn't tell," never a guess.
The honest limits.
  • The 44-session figure is measured on the maintainer's own sessions, not your setup, and isn't publicly reproducible (the frozen corpus is). The 0.1.106 fix was tuned on those 44, so the coming re-measure on new sessions is the number that will count.
  • The detection set is v1 and hand-built: it proves the checks catch the violations we tested and stay quiet on the near-misses, not that they catch every possible real-world violation.
  • It reads one session's recorded transcript. It is solid for the honest case — it is not, today, tamper-evident against someone deliberately covering their tracks.
